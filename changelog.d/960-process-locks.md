### Upgrading (from v0.5.2)

- Locks now record their host, boot, pid namespace and process start identity (#960). A legacy lock or takeover claim without those fields, an unknown place or identity, and a malformed record stay busy. This includes stale locks on systems where these details cannot be read (on platforms without a known process place). Once no holder runs, an operator must remove such a record before its resource can be acquired again. A live claim no longer expires just because it is old.
- Stop every old process sharing lock resources before upgrading. New locks retain a per-resource `.<filename>.flock` inode and hold its native lock until release; old binaries do not participate. Guard inodes are machine-local, excluded from exports/imports, and never removed by normal cleanup. Offline maintenance may reclaim accumulated guards only after all users stop.
- Native locks use util-linux `/usr/bin/flock` on Linux/WSL2 local ext2/3/4, XFS, Btrfs or tmpfs, and native system-Perl flock on macOS x86_64/arm64 local APFS/HFS. Darwin records its boot session and stored process start timestamp (same-second PID collisions conservatively stay busy). Unknown/network/FUSE/overlay filesystems and missing helpers fail closed. Docker state and slots now use local volume paths; share named volumes across invocations. Native Windows agents continue to require WSL2.

### Guardrail changes: what each one does

- The shared lock reader accepts only bounded regular files, using the existing no-follow, nonblocking descriptor reader on POSIX (#960). A FIFO, link or oversized record cannot hang or redirect a stale-lock read. A stale takeover requires the same known host, boot and pid namespace, plus proof that the recorded process is gone or its pid now has another known start identity. Unreadable identity never proves death.
- A missing process entry while its pid still answers signal 0 (for example with Linux `hidepid=2`) is an unknown identity, never proof that its lock can be taken over.
- Native guards serialize the complete ownership lifetime, including reaping: a delayed claim reaper cannot remove a live replacement claim or let a stale remover delete a live successor's lock. The guard's final contents/mode are published atomically; it survives helper exit, release and crashes. Ordinary children do not inherit ownership. Known-dead holder/claim records still recover automatically; kernel locking does not turn unknown records into proof of death. This assumes cooperating upgraded clients and stable directory entries, not protection against external raw unlink/rename. `test/locks-reaper.test.ts` preserves the deterministic pre-fix failure and tests serialized acquisition, initialization/takeover/release crashes, helper failure and descriptor noninheritance.

- GitHub budget accounting uses the same recovery protocol and no longer renames aged locks outside it. A busy or unverifiable lock keeps the existing soft-accounting fallback: API calls proceed after the bounded wait, without deleting the owner's metadata.
