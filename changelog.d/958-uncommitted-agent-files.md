### Guardrail changes: what each one does

- **An agent run doesn't start when what Claude Code loads from the checkout isn't what its last commit holds (#958).** A project command (a worktree setup step, a dependency's install script) runs as the agent user and could write `.claude/settings.json` with a `SessionStart` hook, or a `CLAUDE.md`, into the checkout. The next agent run loaded it and ran the hook outside any sandbox, because project hooks were allowed ("they only add"). Now anything under `.claude/` (a gitignored file there included, never the coordinator's own `.claude/worktrees/`) and any `CLAUDE.md` that differs from the checkout's HEAD, or isn't in it, refuses the run, naming the files. So does a `.claude` that is a link or not a folder, or a link under `.claude/` (git never looks inside a linked folder). And the `CLAUDE.md` and `.claude/CLAUDE.md` that Claude Code loads up front, from the top down to the run's folder, are compared with HEAD byte for byte, whatever the ignore rules say, so a `.gitignore` the same step writes can't hide one. Every tracked agent file is compared with HEAD byte for byte too, and a `--skip-worktree` or `--assume-unchanged` flag on one refuses, so git can't be told to look away. A committed link (`.claude/skills -> ../skills`, or `.claude` itself) is allowed while it is as committed, its target is in the checkout, and the target holds nothing HEAD doesn't. An empty, untracked file (the mount points Claude Code's sandbox leaves on Linux) doesn't count. The same files in folders above the checkout that sit in another checkout (task worktrees under the main one) are compared with that checkout's HEAD, and so are a `CLAUDE.md`'s and a `.claude/rules/` file's `@imports` and a subfolder run's own `.claude/`. Names are folded on case-insensitive file systems, and a committed link to a file HEAD doesn't hold refuses. The check runs again right before claude starts. A sparse checkout's left-out files, line-ending conversion, and `settings.local.json` and `CLAUDE.local.md` (which these runs don't load) don't refuse. A checkout whose status can't be read refuses too, and so does one git can't read at all while a `.git` is there (a garbage worktree `HEAD`, a rewritten `gitdir`), and a FIFO or other non-regular entry under `.claude/`. Not covered: an ignored `CLAUDE.md` deeper in the tree, as under `node_modules`.
- **A guarded agent run loads nothing from its checkout (#958, the owner's decision).** It now starts Claude Code with `--setting-sources ''`, as planner runs already did. So no project settings, hooks or `CLAUDE.md` (a parent folder's included, measured with Claude Code 2.1.319) reach it; its settings are the instance's own. That closes the race a check can't: a hook written while claude starts. Project permission rules and hooks no longer apply to guarded runs. The checks above stay as a second line.
