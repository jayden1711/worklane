### Guardrail changes: what each one does

- **Direct land holds the categories PR mode always holds for a human (#716).** `land_mode: direct` skips the merge decision. So a change in a category PR mode always holds for a human (review.yaml's L3 categories, CI config, the agents' own instructions, the harness's own controls, the odd paths, the repo's `merge.wait_categories`, and dependency manifests) could land at L0 to L2 with only the evaluator's approval. Such a change is now raised to L3, and the owner is asked, with the same reasons the merge policy gives in PR mode. The reasons read `high-risk: <category> (<paths>)` for a category, and `design: dependency manifests change (<paths>)` for a manifest. The floor is checked twice: once when the worker's change gets its level, and again just before the push, on the commit the land would push (R1182f). That second check always runs, also when every entry is approved (R1182h). It covers what a `tests.yaml` `land.pre` step or a gate wrote, and uses the review config and `land_mode` in force at landing, so a change queued in PR mode or before a wait category was added is caught. A file counts as an entry's own only while it is exactly as at that entry's head: the same content, mode and type. One that changed is output, and no approval given at review time covers output. If the check finds a reason, nothing is pushed. Each entry the owner hasn't approved goes back to the owner (L3); with none, every entry does, unless the owner already approved, at landing, exactly this batch and land commit (R1182i/j). The entry's level names every judged file with its mode, type and object, never "and N more", and records a hash of the batch's entries, the held categories, and every judged file a held reason is about (R1182n, R1182p): an ordinary file that changes on every pass, such as a build stamp, raises nothing on its own and so never makes an approval stale. A large app change binds the app files it counts (decided by its category, never by the `*` it records, so a file named `*` changes nothing; R1182q), so a docs build stamp never makes an approval stale; a stamp in any file outside the docs and tests globs (app code, or a root `version.json`) is part of the large change, so it does ask again on every pass (R1182r). Each bound file is hashed as it is on main's tip and in the land commit, so an approval never covers a land that undoes a later change main made to that file; main moving through other files changes nothing. An approval counts only while that hash matches, so the same paths with other content, a swapped file, a reason the owner wasn't shown, main's later change to a held file, or another batch is asked again. An entry approved at landing isn't asked again about the identical land commit. The files a held reason names by path are listed first, then the rest the hash binds. Every file name in the question and the level is shown as every reason shows it (escaped when it holds a newline, a bidi override or another odd character), so a file name can't hide the lines after it (R1182t). Entries the owner approved together at landing are batched together again, exactly as approved and with no other entry, so one approval each lands them (R1182t, R1182v). A file name the tracker's redaction would change (a key marker, an email, an address) is listed by its bytes, and each line of a question is redacted on its own, so no redaction can hide the lines after it (R1182v). A line cut at the question's line limit keeps a hash of the whole line (the first 32 hex of its SHA-256), so two names that differ only past the cut still show differently (R1182x, R1182z). The question's comment names as many of those files as fit in one issue comment and says how many more there are and which event names them all; if the comment still can't be posted, the question stays recorded (answerable on the dashboard or with `decide`), the entry's result is written, and the owner's answer is honoured. The land commit is read byte for byte (R1182k, R1182l): each revision's whole tree and the commit's changed paths come from git as raw `-z` records keyed by the path's own bytes, and no path is ever given to git as a pathspec, so a name starting with `:` or carrying pathspec magic means only itself. An entry's own files are its proposed change's paths, read from git by their bytes, never its recorded (decoded) names, so a name with a literal U+FFFD can't borrow the ownership of a non-UTF-8 name that decodes the same way (R1182m). A name that isn't UTF-8 is never an entry's own file, so it is judged as output. If the land commit can't be read that way, the batch is held and the owner asked (no approval can match such a hold); the floor never throws and stalls the queue. The rest of its batch waits. The question is recorded before the entry's result, so a failure before it is recorded leaves the entry queued and asked again, never dropped. Which entry a pre-land step's output came from can't be told, so an owner's approval of it at landing covers that exact output for that exact batch; the entry's level names every file. The rest of the merge decision still doesn't apply to a direct land: the evaluator's binding design flag, a new top-level module, the worker's protected claim (`claimedProtected`), the weakening and vacuity holds (#783, #784), the size limits and its other doubt reasons. Of its three switches, a direct land honours the auto-merge stop and the instance's `policy.yaml` `auto_merge` switch (#808), besides the emergency stop and the branch's protection; it doesn't read `review.yaml` `merge.auto`. The landing floor runs first, so what it holds goes to the owner, and those stops can still hold the push after the owner approves.
- **A comment answers only the question it replies to (R1182v to R1182ab; fixes #1248 for every comment-answered decision).** A decision answered on the issue (`/<cli> approve`, `reject` and the rest) used to take the latest matching reply of any age. So an approval of one question also answered every later question on the same issue: a landing re-ask after the output changed, or a landing question after a review-time approval. That let output land that the owner never approved at landing. Now the tracker's own comment order decides, never a clock (the instance's and the tracker's clocks needn't agree). Each command line in a reply (outside fenced code) is read on its own, with its option and its id taken from the same line. Any `d-…` token after the option on that line is the id it names, also in backticks, in parentheses or after a word, and an id ends at a word character, so `d-12-a3f9c1.` names `d-12-a3f9c1`. The last line naming a decision's id answers it, and a line naming another id never does. A bare line (no id) answers a question only when it is the one open question the reply can be for: that question's own comment is above the reply and unedited, no other recorded question comment (answered or not, edited or not) lies between them, and every other unanswered question on the issue has its comment, unedited, below the reply. Otherwise it answers nothing and records one note (`reply_ambiguous`) with the ids to use. A question posted while the owner was typing an answer to another therefore takes no answer it wasn't given. The question's own comment is the one the coordinator posted, found again by the id the tracker gave back (recorded as `decision.posted`), never by its text, and not once it has been edited. So no one can move it by writing or editing other comments. On GitHub an edit is read from GraphQL's `lastEditedAt`, never from REST's `updated_at`, which a hide also moves; if GraphQL can't answer, every comment counts as edited (fails closed). A question comment the coordinator posted is never itself a reply. The question now shows the id in its reply instruction, and says a reply without the id counts only while it is the only open question on the issue. If its comment couldn't be posted, only a reply naming the id answers it. That is never silent: a question whose comment fails records a `coordinator.error` (`question_not_posted`) naming the id and the ways to answer. A bare reply set aside for that reason records one note (`reply_without_id`) saying to name the id. A command naming an id that no decision on the issue has records one note (`reply_unknown_id`). Both show among the dashboard's errors (under earlier errors after the next clean tick), and the decision stays pending on the dashboard until it is answered. The rule applies to every decision answered by comment (land, plan, question, domain and the others). A reply posted before its question now answers nothing: answer the new question again, on the issue or the dashboard. Out of scope here: a comment someone else edited into an approval keeps its author's name (#1253, on main too).
