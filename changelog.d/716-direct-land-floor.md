### Guardrail changes: what each one does

- **Direct land holds the categories PR mode always holds for a human (#716).** `land_mode: direct` skips the merge decision. So a change in a category PR mode always holds for a human (review.yaml's L3 categories, CI config, the agents' own instructions, the harness's own controls, the odd paths, the repo's `merge.wait_categories`, and dependency manifests) could land at L0 to L2 with only the evaluator's approval. Such a change is now raised to L3, and the owner is asked, with the same reasons the merge policy gives in PR mode. The reasons read `high-risk: <category> (<paths>)` for a category, and `design: dependency manifests change (<paths>)` for a manifest. The floor is checked twice: once when the worker's change gets its level, and again just before the push, on the commit the land would push (R1182f). That second check always runs, also when every entry is approved (R1182h). It covers what a `tests.yaml` `land.pre` step or a gate wrote, and uses the review config and `land_mode` in force at landing, so a change queued in PR mode or before a wait category was added is caught. A file counts as an entry's own only while it is exactly as at that entry's head: the same content, mode and type. One that changed is output, and no approval given at review time covers output. If the check finds a reason, nothing is pushed. Each entry the owner hasn't approved goes back to the owner (L3); with none, every entry does, unless the owner already approved, at landing, exactly this batch and land commit (R1182i/j). The entry's level names every judged file with its mode, type and object, never "and N more", and records a hash of the batch's entries and of every judged file a held reason is about (R1182n): an ordinary file that changes on every pass, such as a build stamp, raises nothing on its own and so never makes an approval stale. An approval counts only while that hash matches, so the same paths with other content, a swapped file, or another batch is asked again. The question's comment names as many of those files as fit in one issue comment and says how many more there are and which event names them all; if the comment still can't be posted, the question stays recorded (answerable on the dashboard or with `decide`), the entry's result is written, and the owner's answer is honoured. The land commit is read byte for byte (R1182k, R1182l): each revision's whole tree and the commit's changed paths come from git as raw `-z` records keyed by the path's own bytes, and no path is ever given to git as a pathspec, so a name starting with `:` or carrying pathspec magic means only itself. An entry's own files are its proposed change's paths, read from git by their bytes, never its recorded (decoded) names, so a name with a literal U+FFFD can't borrow the ownership of a non-UTF-8 name that decodes the same way (R1182m). A name that isn't UTF-8 is never an entry's own file, so it is judged as output. If the land commit can't be read that way, the batch is held and the owner asked (no approval can match such a hold); the floor never throws and stalls the queue. The rest of its batch waits. The question is recorded before the entry's result, so a failure before it is recorded leaves the entry queued and asked again, never dropped. Which entry a pre-land step's output came from can't be told, so an owner's approval of it at landing covers that exact output for that exact batch; the entry's level names every file. The rest of the merge decision still doesn't apply to a direct land: the evaluator's binding design flag, a new top-level module, the worker's protected claim (`claimedProtected`), the weakening and vacuity holds (#783, #784), the size limits and its other doubt reasons. Nor do its three switches: the instance's `policy.yaml` `auto_merge` kill switch, `review.yaml` `merge.auto`, and the auto-merge stop. Direct land checks only the emergency stop and the branch's protection; #808 (PR #1183) brings the stop and the policy switch to it, and whichever of #1182 and #1183 lands second corrects this sentence.
