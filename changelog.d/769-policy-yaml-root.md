### Upgrading (from v0.5.2)

- **Single machine, an existing install: its `policy.yaml` stays the coordinator's until an admin reruns `add-project.sh <name> <owner/repo>` (or runs `sudo worklane policy own <name>`) (#726).** Until then the engine reads it as before and doctor warns. A coordinator-owned policy looser than its coordinator could set through root (`auto_merge: true`, `land_mode: direct`, `sandbox: false`, …) stops that rerun at the policy step, naming `--accept-loose` for an admin who has checked it. The rerun also gives the instance its kill-switch spare: until then, a `policy set <name> auto_merge off` on a full disk fails, naming the error. No switch exists on any install yet, so nothing migrates. Then rerun `machine-helper.sh` with every instance (After install) for the dashboard's `set-policy`.

### Guardrail changes: what each one does

- **Single machine: each instance's `policy.yaml` is root's (#726).** Before, the coordinator user owned it, so anything running as that user could turn `sandbox` off or set `allow_same_user`. Setup now makes it root's (0644, its content kept, its isolation and merge keys printed) and records its path and a sha256 of its content. The engine then refuses a `policy.yaml` that isn't root's alone, isn't the recorded file, or isn't what root last wrote, and the instance stops instead (doctor fails, naming `sudo worklane policy own <name> --retake`). Setup never takes over a policy looser than its coordinator could make it (`sandbox: false`, `allow_same_user: true`, `land_mode: direct`, lanes, and the like): its policy step stops, naming `sudo worklane policy own <name> --accept-loose` for an admin who has checked it. Root changes one key at a time with `sudo worklane policy set <name> <key> <value>`, which never takes `sandbox` or `allow_same_user`. `sudo worklane policy set <name> auto_merge off` arms a root kill switch and nothing else: no lock and no read of `policy.yaml`, so nothing can stop it, and it needs no free space (a disarmed spare is renamed). Switches are keyed by a stable instance id, never by name (`/etc/worklane/policy-root/<name>.id` names `by_id/<id>/`), so a rename shares them from its start and never carries one. While one is there auto_merge is off, whatever `policy.yaml` says, until root's `policy set <name> auto_merge on`, which clears only the switches that were there before it started, so an OFF given meanwhile stays. The dashboard never writes a root `policy.yaml`: its changes (Settings, the Policy form) go through the machine helper's new `set-policy`, run by the coordinator, which takes the same keys and never a loosening; the dashboard says such a change is queued until the helper has run it. On every install, root's policy or not, the dashboard only tightens `land_mode`, `main_watch` and `auto_merge` (to `pr`, `auto` and off; principle 6): `direct`, off and on are an admin's, at a root shell or by editing `policy.yaml` (or the Helm value). Every other key only tightens from the dashboard too, on every install (the owner's decision): the value in effect is its ceiling, so budget, workers and every cap only go down, a switch only goes off (automations, `ci_repair`, `research.repo_access`), `stuck_guard` only goes toward on and `run_windows` only narrows. Root's `policy set` holds the coordinator's route to the same rule. A raise is the admin's: root's command, or an edit of `policy.yaml` where root never took it over. The three tightenings are listed whole in sudoers, so they work on every sudo; on a sudo older than 1.9.10, which has no `set-policy` pattern rule, the dashboard asks for nothing else and names the root command.
