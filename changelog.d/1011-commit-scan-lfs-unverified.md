### Upgrading (from v0.5.2)

- In a checkout with the standard git-lfs filter configured, an agent's commit is now refused when `git-lfs` isn't a program only root can change and either of these holds:
  - any attributes source of the checkout names `filter=lfs`, whether or not a file matches it now. That means an attributes file in the working tree (tracked, untracked or ignored), in the index or in HEAD, the repository's own (`info/attributes`), the user's (`core.attributesFile`, a relative one read from the checkout's top as git does) or the system's. A tree named as the attributes source (`attr.tree` in the config, or `GIT_ATTR_SOURCE` in the guard's environment) counts as naming it, as does a source that can't be read;
  - the line runs a `git mv` naming an attributes file (any file called `.gitattributes`, whatever it holds) before the commit.

  The program fails that check when it is one of the user's own (for example a user-level install, or a Homebrew, linuxbrew or conda one owned by the user), is reached through a link or folder someone else can change, or is looked up through an empty or relative `PATH` entry. No git-lfs found, or native Windows (which has no file owners to check), also refuses. git's own exec path is checked first, as git looks there first. In checkouts where no attributes source names the filter, git-lfs isn't checked and the commit isn't refused on this ground, even where `git lfs install` set the filter up in the global config. git doesn't run git-lfs as a filter there, but the hooks `git lfs install` writes (`post-commit` and the others) still run whatever `git-lfs` PATH finds, a user's own included (#1110, as on earlier versions). The exception is a line whose `git mv` names an attributes file, which is refused even when that file only sets line endings. To commit after such a `git mv`, run it in a call of its own, then commit. Otherwise, install git-lfs where only root can change it, or have a person commit in those checkouts.
- In such a checkout, a file the commit records that is over 1024 bytes, names a pointer version in its first 1024 bytes and isn't the exact pointer form is refused, as smaller ones already were. Stage it in an earlier call (git-lfs then stores the exact pointer), then commit. What the file held before the commit is not refused on this ground.

### Guardrail changes: what each one does

- **The commit secret scan refuses the large-file cases it can't verify (#1011).** git-lfs reads a file of any size as a pointer from its first 1024 bytes and ignores the rest, so such a file could name an object the scan never read. That now refuses the commit. A `git-lfs` program the agent's user could replace could change what is stored after the scan has read it, so it is checked wherever an attributes source names the filter. Attribute settings that reach only the agent's shell (its startup files, `GIT_ATTR_SOURCE`) and its PATH are not seen. The push gate still scans what leaves the machine.
