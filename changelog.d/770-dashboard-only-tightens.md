### Upgrading (from v0.5.2)

- **The dashboard no longer sets `land_mode: direct`, `main_watch: off` or `auto_merge: true` on any install (#726, #770; the owner's decision, principle 6).** The Policy form offers only `pr`, `auto` and off for them and names the admin's route for the rest: on a laptop, cloud or VM install, edit `policy.yaml` (or its Helm value); on a machine, `sudo worklane policy own <name>`, then `sudo worklane policy set <name> <key> <value>`. A policy already set that way keeps running as it is.
- **The dashboard only lowers budgets, workers and caps, and only turns settings off, on every install (#726, #770; the owner's decision of 2026-10-19).** On a laptop, cloud or VM install too: raising `budget.daily_usd`, `agents.max_workers`, a Settings cap, the attachment size or retention, widening `run_windows`, turning `automations`, `ci_repair` or `research.repo_access` on, or moving `stuck_guard` toward off is refused, naming the admin's route: an edit of `policy.yaml` (or its Helm value) there, which has no root command, or root's `policy set` on a machine. An intake cap is compared with the one in effect, `intake.yaml`'s where `policy.yaml` sets none. Lowering and turning off work as before, with two exceptions. On a machine whose `policy.yaml` is root's, lowering `ci_repair.max_fixes_per_pr` or narrowing `run_windows` while the repo's config sets them is refused up front, naming root's `policy set`: root can't tell the value in effect, and once `policy.yaml` holds it, lowering works. On any install, an intake cap `policy.yaml` doesn't set can't be changed while `intake.yaml` doesn't load (on a machine whose `policy.yaml` is root's: as root reads it, so not through a link, a second name or past root's size limit).
