### After install

- **The same rerun (or, from then on, the release channel's self-update) installs the updater that judges each required check by its source (#727).** The engine's own checks (the default `required_checks`) are pinned to their workflow files by the updater itself, so nothing else is needed. A check added with `--add-check` that isn't one of them is judged by name, as before, until root pins it in `/etc/worklane/updates.json` `required_check_sources` (`{"<name>": {"workflow": ".github/workflows/<file>"}}` or `{"<name>": {"app_id": N}}`), or the repo's branch rules name its App.

### Guardrail changes: what each one does

- **The engine updater counts a pinned required check only from its source (#727).** The pin comes from `updates.json` `required_check_sources`, else from its own fixed list of the engine's checks and their workflow files (`ENGINE_CHECK_SOURCES` in `scripts/machine/worklane-update.cjs`, never read from the commit judged), else from the App the repo's branch protection or ruleset requires. A workflow pin needs GitHub Actions to have posted the check from that file's workflow run, in the repo, for that very commit, as one of that run's own jobs (its page `/<repo>/actions/runs/<run>/job/<id>`). A same-name check from another App or workflow, or one posted onto the commit from another commit's run or through the API, doesn't count. A pinned check's own Actions runs are grouped by workflow file (a pin to GitHub Actions' App is judged per file too); in every group the latest run (by the runs' own order) and the newest check run must both pass. A pin to an App that isn't Actions can't be split by file: that App's latest check run of the name on the commit decides, in whatever check suite, so a later pipeline or re-run of that App supersedes its earlier ones (the owner's decision). Any run of its name from any other source that isn't a pass refuses the commit, and so does a commit status of its name that isn't success (pending waits; a status read GitHub refuses at all, a 403 or 404 included, gives no answer and waits: the owner's decision) (the owner's rule). A required check nothing pins is judged by name, as before; unread branch rules, workflow runs or statuses make the commit wait; an invalid pin refuses it. **The ways it is looser than judging by name** (both the owner's decisions): a pinned workflow file's later run on the commit supersedes its own earlier failed or cancelled runs, and a pinned non-Actions App's later run supersedes its earlier ones. While a required check is pinned, every pager (check runs, workflow runs, statuses) reads on past a full page whatever `total_count` says, and one still full past 10 pages gives no answer (the commit waits), never a truncated list to judge. With every required check a bare name (nothing in `updates.json`, `ENGINE_CHECK_SOURCES` or the branch rules pins it), the updater makes main's reads of the commit's checks and gives main's verdict. **The read cost, for the owner to weigh:** a commit whose check runs could still make it installable costs two more unauthenticated reads (its workflow runs and its combined status; one when it's missing, red or still running on its check runs alone, as on main). A machine waiting on a green tip makes 4 reads a run instead of main's 2 (24 an hour instead of 12, at one run every 10 minutes); the first sight of 20 red or idle commits costs 21 reads, as on main; but 20 commits that each pass every check by name and still fail a pinned check (a pinned file's later run failed) cost 61 reads in one run, more than GitHub's 60 an hour per IP. Past the limit each read gets no answer and the update waits (never a wrong install), for up to an hour.
