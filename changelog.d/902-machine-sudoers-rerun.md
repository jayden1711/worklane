### After install

- **Check the machine helper's sudoers rule once (#898).** `sudo bash /opt/worklane/current/scripts/setup/machine-helper.sh --check` only reads, and answers one of:
  - `current` or `absent`: nothing to do.
  - `stale`: the installed rule is in the engine's own shape and the rewrite only drops whole commands or users. Rerun with no flag, adding no user: `sudo bash /opt/worklane/current/scripts/setup/machine-helper.sh --may-add= <every instance>`.
  - `wider`: anything else. That covers a machine coming from v0.5.2, whose engine rule adds set-policy (#726), and an installed rule edited outside the engine's shape. It prints a unified diff headed `--- installed /etc/sudoers.d/worklane-machine` and `+++ engine (machine-helper.sh)`. It then prints the command `sudo bash /opt/worklane/current/scripts/setup/machine-helper.sh --replace-sudoers=<pin> <every instance>`, where `<pin>` is the sha256 of exactly that diff's rule. Read the diff, then run that command. If the engine's rule changed in between, it installs nothing and prints the new diff and a new pinned command.

  The updater keeps the helper itself in step with the engine, never its sudoers rule, so a rule an older engine wrote stays until you run that.
- **An instance named `machine` or `console`, if a machine has one (#902):** those names are reserved now, since that instance's sudoers file is the machine helper's rule's or the owner console's. Nothing new is made under either. What still works for an instance that already has one: its coordinator loads, it exports, and the hub serves it. `sudo worklane policy set <name> auto_merge off` works at any time. Any other tightening works once its policy is root's: a first `sudo worklane policy own <name>` makes it so, with `--accept-loose` when the file is looser than its coordinator could make it. The experiment and test-run helpers still stop, wipe, prune and check what it has, and its test user still counts as one, so other instances' test runs keep their own user namespace. `instance-remove.sh` removes it. What stops: it starts no test run or experiment job of its own, and the engine leaves it out of the machine helper's rule. The helpers' `check` still makes and runs root's own fixed probe under its test, job and scorer users, as for any instance. The next add-project, rename, removal or `--check` rewrite drops its coordinator from the rule, so its dashboard's machine requests stop working. Its root policy is never taken over with `policy own --retake`. If its coordinator replaced the file root wrote, the gate keeps refusing that file, and the messages name the instance's removal as the way out. Remove it with `sudo bash /opt/worklane/current/scripts/setup/instance-remove.sh <name>` and add it again under another name.

### Guardrail changes: what each one does

- **The machine helper's sudoers rule is rewritten on its own only when it narrows, failing closed (#898).**
  - add-project's machine-helper step is done only while the rule is the engine's, byte for byte.
  - Otherwise a rerun rewrites it, through `machine-helper.sh`, only when the installed rule is in the engine's own exact shape and the engine's rule only drops whole commands or users from it. The shape is: comment lines, one `Cmnd_Alias WORKLANE_MACHINE` in the engine's formatting, and one `<users> ALL=(root) NOPASSWD: WORKLANE_MACHINE` line.
  - The one user a rewrite may add on its own is the coordinator of an instance being created. `instance.sh` puts the name on root's list (`/var/lib/worklane/add-project-new`, root's 0600) only when nothing of that instance is on the machine yet: none of its users (`wl-<name>`, `-agent`, `-eval`), no `/srv/worklane/<name>`, no hub entry and no place in the rule. That holds whether it runs from add-project, by hand, or from a rename. Every `machine-helper.sh` run takes off each name it writes into the rule. A name counts only when the list is a regular, unlinked file of root's, mode 0600; anything else marks nothing. So a coordinator root takes out of the rule is not put back without the flag, even when root also deleted its user by hand and add-project makes it again: its agent user, checkout or hub entry is still there.
  - Anything else waits. That covers a command or user the installed rule lacks, a second spec or alias, a tag, a `Defaults` or include line, a negation, an escape, or a CR. `add-project.sh`, `machine-helper.sh` and `instance-rename.sh` change nothing; the rename checks this before its first change. They print the unified diff and, on the line after it, `rerun as root with --replace-sudoers to install the engine's rule: <command>`, and add-project waits (exit 3).
  - **No pin in what the dashboard shows.** add-project's JSON output (the waiting detail the dashboard stores and shows, with no diff beside it) never carries a pin. It says the rule would widen and points root at a root shell: rerun the same add-project there, or run `machine-helper.sh --check`. Either prints the whole diff with the command pinned to it. A waiting add-project also prints that diff and pinned command on its stderr. When a coordinator's dashboard started it, through the machine helper, that stream reaches the coordinator's process, which keeps only the JSON's waiting line. The pin isn't a secret: it is the sha256 of the engine's rule, which anyone can compute, and only a run at a root shell can pass it.
  - **A removal never waits on a widening.** `instance-remove.sh` takes the instance's coordinator out of the rule first, before its export, its registry's items or any user goes. When the engine's rule for the other instances only narrows the installed one, it writes that. Otherwise (an older engine's rule, say) it runs `machine-helper.sh --drop=<name>`, which takes that one user out of the installed rule and changes nothing else, under the lock; the widening stays a separate step for root (`--check`). That step is decided under the lock add-project and instance-rename hold. It stops the removal, changing nothing, when the installed rule isn't in the engine's own shape: root first installs the engine's rule for the other instances with the pinned `--replace-sudoers=<pin>` command it prints (the owner's decision: fail closed). It also stops when the rule changed under it; then run it again. The other instances it rewrites the rule for are those `machine-helper.sh` takes: one named `machine` or `console` is left out, a narrowing.
  - **A rule taken away is not put back on its own.** No installed rule counts as a first install only on a machine that never had the helper set up (no `/usr/local/libexec/worklane-machine`, no `/etc/worklane/helper-rules.json`). Where root deleted the rule, or moved it aside, to revoke the helper, the next rerun or `machine-helper.sh` run shows the whole rule it would add and waits for `--replace-sudoers`. The same holds after `instance-remove.sh` takes out the last instance: the helper stays installed, so the next add-project waits for the flag.
  - `--replace-sudoers=<pin>` is root's, at a root shell: the machine helper runs `add-project.sh` with exactly a name and a repo, so a coordinator's add-project can never pass it. Every printed command carries the pin (sha256) of the rule its diff showed. A run installs only a rule with that pin: if the engine's rule changed (a release landed, say), it writes nothing and prints the new diff and a new pinned command. A bare `--replace-sudoers` is refused.
  - **`machine-helper.sh` is the one check, at write time.** add-project passes it only the user it may add (`--may-add=`), never trust in every name. Every machine-helper.sh command the engine prints without a pin carries `--may-add=` too: add-project's "this step alone" retry and `--check`'s `stale` command.
  - **One lock, only root's.** The engine's writers of this rule are `machine-helper.sh` (its `--drop` too) and `instance-remove.sh` when it takes the rule away or removes an old instance named `machine`. Each holds one lock, `/run/worklane-machine/sudoers.lock`, from its check to its write. The lock sits in a directory only root can enter (root's, 0700), so no other user can open, hold or plant it. A run with no `flock`, or with that directory anything else, refuses to write. A root writer outside the engine takes no lock.
  - **`machine` and `console` are no instance's name.** `instance.sh` writes an instance's own sudoers file, `/etc/sudoers.d/worklane-<name>`, with no lock, check or pin. So an instance named `machine` (accepted until now, by the coordinator's `add-project` route too) would overwrite the machine helper's rule. `console` would overwrite the owner console's file. Both names are refused in `lib.sh`, the machine helper, the engine and the testrun and experiments helpers' copies. Every fixed sudoers file the setup scripts write is listed in the engine's `ENGINE_NAMES`, whose test refuses any instance name that would map onto one. An instance made under either name before keeps working where it is, outside the machine helper's rule (see After install), and `instance-remove.sh` removes it, its export first. For `machine`, its file is the one the helper's rule uses, so it goes whole under the lock, and the next add-project waits for `--replace-sudoers`.
  - **What is checked at the write.** Right before `install_sudoers`, and again inside it after `visudo` and right before the move:
    - the temp file must be byte for byte the rule checked;
    - the installed rule must still be byte for byte what the first check read;
    - the new rule must still only narrow it, or carry root's pin.

    A first install (no rule, the helper never set up) is decided once, at the first check, because the run installs the helper before it writes the rule. Otherwise nothing is written (exit 3).
  - **The window left:** from the last check's read of the installed rule (`install_sudoers`' precommit, `lib.sh` line 92) to the move (`mv`, line 93). Any root writer that takes no lock can land there: a hand edit, `visudo` or `rm` at a root shell, or an older release's scripts (their `instance.sh` for an instance named `machine` among them). An `rm` in that instant is undone by the `mv`.
- **The updater names a stale or wider machine helper rule (#898).**
  - On every run, updates on or off, the updater runs the installed engine's `machine-helper.sh --check` as root.
  - It runs the check only when the engine's real path has no link below the engine directory, and when the script, its `lib.sh`, and every directory up to `/` are root's and writable by no one else. It then runs bash on that resolved path.
  - A stale or wider rule goes to the updater's journal and is raised as a `machine_sudoers_stale` incident. The detail says which case it is.
    - For `stale`, the fix is the rewrite command, with `--may-add=`.
    - For `wider`, the fix is `machine-helper.sh --check` at a root shell, which prints the whole diff and the command pinned to it. The incident gives a count of the lines added and dropped, never a pinned command beside a diff cut to fit.

    A current rule closes the incident.
  - The updater never writes the rule and never holds an update on it.
