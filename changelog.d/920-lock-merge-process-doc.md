### Upgrading (from v0.5.2)

- **The planners' decisions index reads only committed records, and fails closed.** A decision record (a decisions file, or an entry in a decisions folder) is indexed only when git tracks it at the plan's base commit as a regular file, and its text is read from that commit. A record that is only in the working tree (untracked, or left by a setup or install step), an uncommitted edit to one, and a record committed as a symlink are no longer indexed, so a plan can't cite them. And when the checkout has a `docs/process.md` that can't be read (for example a symlink loop, or a folder the engine can't search), no decision record is indexed. Plans can still cite the decisions already made. A managed app that kept a record uncommitted or behind a symlink commits the text at the record's own path, or plans citing it are refused.
- **A decisions folder with a broken entry no longer stops planning.** An entry that is a dangling link used to throw and end the plan step; it is now skipped, and the folder's committed records are indexed.

### Guardrail changes: what each one does

- **The engine repo's merge process waits for the owner.** In the engine's own repo, a change to `docs/process.md` (how the repo's own PRs are merged and reviewed) is now self-modification: L3, and never auto-merged, whatever `review.yaml` says. The engine's own `review.yaml` also holds it under `engine-guards`. A managed app's file of the same name keeps the categories its own `review.yaml` gives it.
- **Two checks keep the page out of the planners' decisions index on the routes they cover.** They don't close every route (below).
  - The index reads only records committed at the plan's base, as regular files at a decision record path, and never the working tree. It reads the base commit, its trees and the records from the instance's own clone, not through the worktree's `.git` file, and checks every object against its id, so an object store that maps a real id to other text (git doesn't check a packed object's hash on read) indexes no record. As a second check, it leaves out a record that is the checkout's `docs/process.md` under another name (a hard link) or whose real path isn't a decision record path inside the checkout. It can't recognise a copy of the page's text. These checks cover what the base commit holds, not which commit is the base. Known routes they don't close, such as who picks the base (#962) and text in decisions already made (#956), are listed under "Open routes into the decisions index" in `docs/process.md`. Reviews found them one by one, and that list is not proven complete. The by-design closure is #975 (open): planner runs will take input only from an allowlist enforced in code.
  - So, in the engine's own repo, every decision record path (`decisions.md`, `DECISIONS.md`, `docs/decisions.md`, `docs/DECISIONS.md`, `.worklane/decisions.md`, `docs/design.md`, and the folders `decisions`, `docs/decisions`, `docs/adr` and `.worklane/decisions` with everything in them) and the index code (`src/plan-decisions.ts`) are now self-modification too, and listed under `engine-guards`. A PR that brings a copy of the page, whole, in part or reworded, into a committed record waits like the page itself. That PR is not the only way in (see the open routes in `docs/process.md`). The lock reads the index's own lists, so a path the index reads is locked by the same change. `test/plan-decisions.test.ts` is locked the same way. A managed app's decision records keep the categories its own `review.yaml` gives them.
- **A removed line in the index code raises the "may weaken a check" hold**, as one in `src/review.ts` does (`src/plan-decisions.ts` is a guard file).
