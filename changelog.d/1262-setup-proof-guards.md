### Guardrail changes: what each one does

- **Setup's login proof loads nothing either (#1262, #958).** `scripts/setup/lib.sh`'s one real call that proves an agent user's Claude login (`claude -p "Reply with the single word: ok" ...`) ran with every setting source, so a hook or `CLAUDE.md` in that user's home loaded with it. It now ends with the engine launch's guards (`--settings '{}' --setting-sources '' --strict-mcp-config`), keeps Claude's auto memory off, and runs in an empty folder that user makes for it, removed after (only a folder `mktemp` made under `/tmp`).
- **A lint holds the repo's scripts to the same rule (#1262, the owner's decision).** `test/claude-launch-shell-lint.test.ts` fails closed. In every shell script (by extension or shebang, anywhere, `.githooks/` included), workflow and composite-action step, Makefile recipe, `package.json` script, Dockerfile `RUN` line, and JavaScript or TypeScript file under `scripts/`, any word that is the claude binary (its name, a path, its npm package or its `cli.js`) is a call, whatever launches it, unless a known non-launcher (`install`, `rm`, `command -v`, `echo`, …) holds it as data. A call must end with exactly `--settings <json> --setting-sources '' --strict-mcp-config`, each flag only once and no `--mcp-config`, or be a pinned exception (`--version`, `auth status`, `auth login`, and two named CI steps). Strings run by `-c` or `eval`, and `$(…)` and backticks, are read too. Its limits (an alias or function defined elsewhere, a variable from another file or the environment, a command built at run time) are named in the test.
