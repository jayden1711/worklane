### Guardrail changes: what each one does

- **A test process no longer lets the children it starts reach the machine's own host tools (#991).** The test preload (`test/isolate.ts`, which every test process runs) wraps Node's child_process. Every child then finds a recording stand-in first on its PATH for each host tool that PATH would find on the machine: sudo, systemctl, systemd-run, journalctl, useradd and the other user tools, visudo, nft, docker, gh, tailscale, claude and the like. A stand-in records the call and fails. It also refuses what it can see would get past the stand-ins: a host tool named by its path from a test, and `env -i`, `command -p` or a login shell that runs a host tool. When the engine's own code runs a host tool by path, it gets the stand-in instead.
  - Before, `test/add-project.test.ts` ran add-project with the real PATH, and since #904 every fresh run asked the machine's real `sudo -H -u <coordinator>`. On a developer machine, doctor's tests ran the real `claude --version`.
  - The exceptions are checked against the calling test file and may only shrink. The setup scripts' own CI-only acceptance test starts its children untouched. Five CI-only acceptance runs take the real sudo, visudo or systemctl through `machineTool`.
  - Not covered: a script that sets its own PATH, a login shell or `env -i` that reaches a tool only through a function it calls, a Worker, and code that patches the builtins after load.
  - gitleaks is not stood in: it only reads, and the secret-scan tests run the real one.
  - Nothing changes for an install: only the tests changed.
