### Guardrail changes: what each one does

- **A change that takes a use away from a registered check table waits for the owner (#941).** The weakening hold reads tables from lines. So a PR could add a new table under another name, move every use of the registered table to it, and leave the registered table and its mark unchanged and unused, and the hold saw nothing. Now a removed or changed line, in any changed file, that names a registered table outside the table's own lines makes the change wait. So does a line that names a module-level alias of the table (`const rules = CHECKS`, in that file or imported into it), or a line in the same statement as a use (`const rules =` with `CHECKS;` on the next line). Every registered table counts, also one whose file the change leaves alone. That covers a decoy declared in the same file, one imported from another file, and a use in another file moved to it. Outside the table's own file, an added line that names it (or an alias of it) waits unless every use there is a plain read, so a shadowing local and any write (`CHECKS.splice(0)`, `CHECKS['splice'](0)`, `CHECKS.length *= 0`, `[].splice.call(CHECKS)`) wait; so does an import of the table's file (or an alias's) taken away or changed (a namespace import, a `require`, an `export *` barrel), and a re-pointed `package.json` `"imports"` entry. Adding a plain read of it (`.length`, `.includes(...)`, a `for ... of`), changing lines that never named the table, and another file's own variable of the same name still pass; any other added use of it outside its own file waits, even a harmless one. Part of #941: still open, until registered tables move to data-only files, are a function declaration or a class field that returns or holds the table, a loop over it kept with its body made dead, an alias more than two imports deep, and a redirect through tsconfig (#1236) (named in the design notes).
