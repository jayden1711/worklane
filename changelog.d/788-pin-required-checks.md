### Upgrading (from v0.5.2)

- **Required checks can be pinned to their source (#727).** A pinned required check counts only from its source: `config.yaml` `required_check_sources` (`{ app_id: N }`, the GitHub App that posts it, or `{ workflow: .github/workflows/<file> }`, the Actions workflow file that runs it), else the App GitHub's own branch protection (`app_id`) or ruleset (`integration_id`) requires for it. A check of that name from anything else, or a commit status, counts as missing. A pinned check's own Actions runs are grouped by workflow file; in every group the latest run (by workflow run, then check run) and the newest check run must both pass. A pin to an App that isn't Actions can't be split by file: that App's latest check run of the name on the head decides, in whatever check suite, so a later pipeline or re-run of that App supersedes its earlier ones (the owner's decision). Any check of its name from any other source that isn't a pass blocks it: another App, another workflow, a run for another head, a commit status. So one workflow file never supersedes another, and a re-run that failed after a newer run passed still blocks. PR readiness and the main watch judge a pinned check through one function over the same facts, the watch as they stood at merge time. This can hold a pinned PR on another App's failing check. **The ways it is looser than judging by name** (both the owner's decisions): a pinned workflow file's later run on the head supersedes its own earlier failed or cancelled runs, and a pinned non-Actions App's later run supersedes its earlier ones, so a failure judging by name would have held no longer holds once that source runs again and passes. **A check nothing pins is judged by name, exactly as before:** nothing changes on upgrade for an install without pins (no PR held, no main-watch stop, no canary rollback; with no judged check pinned, the checks are read as before too, page for page, whatever other check is pinned), except in the window before GitHub's protection and rules first answer the coordinator: until then a check config.yaml doesn't pin counts as missing (no PR is marked ready) and the main watch waits at a merge's checks (a direct push or a bot's merge is still flagged at once). Where GitHub's protection or ruleset names an App, that pin applies at once: it tightens, except for the same-file supersede above. To protect an existing install, after installing this release (an older engine rejects the new key): `worklane doctor` (`required check sources`) names the required checks with no pin; pin each in `config.yaml` through a PR. Gating PRs nobody here wrote is governance mode's job (#704): it refuses to turn on while any required check has no pin (`governanceRefusal`).

### Guardrail changes: what each one does

- **A pinned required check is matched by its source, not its name alone (#727).** PR readiness, the check of main after a merge, fix-forward, the PR batch's fast checks and the main watch keep a pinned GitHub check only when it came from its pinned source (`src/check-source.ts`); a workflow pin also needs the workflow run to be in the project's repo, for the very commit judged, with the check run one of that run's own jobs (its page `/<repo>/actions/runs/<run>/job/<id>`). A pinned check's own Actions runs are grouped by workflow file (the main watch reads the workflow runs whenever a pinned name has an Actions run, as readiness does), and in each group both the latest run, by the runs' own order (the later workflow run, then the later check run, as a re-run attempt is), and the newest check run must pass; under a pin to an App that isn't Actions that App's latest check run of the name decides, in whatever suite (the owner's decision); any non-pass of its name from any other source blocks it, a commit status included. Readiness and the main watch share one judging function (`pinnedVerdict`) over GitHub's latest check run per check suite, the workflow runs and the latest status per context; the watch takes them as they stood at merge time, and when a check being judged is pinned (fix-forward judges its episode's names), both read every page of check runs and statuses, up to 10 (by name, only the pages main read). Then a read past 10 pages, or refused part-way (a rate limit, or a later page's 403 or 404), never judges: readiness throws (the PR waits), and the main watch asks again, or past its pages judges the merge unaccounted; a status read refused at all waits, a first page's 403 or 404 included, so an install whose token can't read commit statuses holds every pinned check (the owner's decision); with no judged check pinned, statuses are read as on main. With no judged check pinned (and GitHub's rules read), both make exactly main's reads (no workflow runs, main's pages) and give main's verdict, whatever other check is pinned. It turns a match into missing, with one exception the owner decided: a pinned file's later run on the head supersedes that same file's earlier failed or cancelled runs. Every judging function takes `JudgedChecks`, which only `PinnedChecks.of` makes, reading its facts itself (the backlog's checks, and under No CI the event log's test runs, which used to be merged in by `headChecks` and `withTestRuns`, both gone); `readiness` and `requiredOutcomes` throw at run time on an array not made there or since changed (a module-private WeakSet; the array and its checks are frozen), so a cast or an `any` around a raw read throws. Type-based scans (`test/raw-check-reads.ts`) also flag any cast into it, any `any` or `never` value or generic or type predicate where it is expected, any raw read however spelled outside the three files that may (each with why), the `src/` routes to `PinnedChecks` outside `merge-flow.ts` that it lists (found by the compiler's module resolution: a name through an alias or barrel, `export *`, `export * as`, a namespace or dynamic import, `require()`, `createRequire` named as such; not `createRequire` by a computed key, `process.getBuiltinModule`, an import inside `new Function`, or `this.pinned.constructor` in a subclass), and any `src/` import from `test/`. What the run-time check can't catch (a `PinnedChecks` over a stand-in backlog) is left to that lint. An unpinned check is judged by name, as before. Reads only: each check run's `app` and its suite's workflow run (`GET /repos/{o}/{r}/actions/runs?head_sha=`), the branch's protection summary (`GET /repos/{o}/{r}/branches/{branch}`) and its rules (`GET /repos/{o}/{r}/rules/branches/{branch}`, every page). Only a first rules page refused for permission or a 404 means no rulesets; a rate limit keeps the last answer (or leaves the rules unknown), never drops a ruleset's pin. Without Actions read access a workflow-pinned check counts as missing, and an Actions run whose workflow run wasn't read never passes a pin. Governance mode (#704) must refuse to turn on while any required check has no `required_check_sources` entry (`governanceRefusal`).
