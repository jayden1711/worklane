### Upgrading (from v0.5.2)

- A sandboxed agent command that reads a file in the project's `secret_paths` (for example tests loading `.env` through dotenv) now reads nothing: the sandbox hides it. Before, only a command naming the file was refused, by the guard hook.
- A guarded agent run whose task file or project guardrails can't be read, or whose `secret_paths` or hidden paths hold a pattern the sandbox can't take as written (`[` or `]`, or a glob starting with a wildcard), no longer starts; the run's detail says why. Before, it started and the hook refused its calls. A `[` or `]` in a checkout's path, the home or a file name is fine: it's passed as `?`, which still hides that path.
- A run whose task hides paths doesn't start when the repository's chain of git alternates can't be followed in full: git reports it deeper than it follows, a file it can't read, or a store that isn't there.

### Guardrail changes: what each one does

- A task's hidden paths and the project's `secret_paths` are denied by the OS sandbox (`sandbox.filesystem.denyRead`) and by `Read(...)` deny rules in every guarded agent run's settings, not only by the guard hook (#890). They are resolved under every checkout of the run's repository, and `~/` under the run's home. A worktree made while the run goes on is covered too, through a glob over each place worktrees are made (the project's `worktree.root`, the engine's own, and each existing worktree's parent), except for a pattern an exception overlaps. The guard hook matches these paths only inside the run's own checkout. A glob an exception overlaps (`!./.env.example`) is passed as what it matches when the run starts, so the exception stays readable. With the sandbox off, the Read rules still apply.
- A run whose task hides paths (an experiment's) is also denied the repository's git object stores (`objects`, every store in the alternates chain as git itself lists it, `lfs`), so `git show <rev>:<hidden path>` can't read a hidden file that was deleted from the worktree.
