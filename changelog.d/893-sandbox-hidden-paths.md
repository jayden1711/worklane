### Upgrading (from v0.5.2)

- A sandboxed agent command that reads a file in the project's `secret_paths` (for example tests loading `.env` through dotenv) now reads nothing: the sandbox hides it. Before, only a command naming the file was refused, by the guard hook.
- A guarded agent run whose task file or project guardrails can't be read, or whose `secret_paths` or hidden paths hold a pattern the sandbox can't take as written (`[` or `]`, or a glob starting with a wildcard), no longer starts; the run's detail says why. Before, it started and the hook refused its calls. A `[` or `]` in a checkout's path, the home or a file name is fine: it's passed as `?`, which still hides that path.
- A run whose task hides paths doesn't start when the repository's chain of git alternates can't be followed in full: git reports it deeper than it follows, a file it can't read, or a store that isn't there.
- A guarded agent run doesn't start when no config folder is found at or above its working directory (the guard hook denies every call of such a run anyway); a run that can use no tool (the experiment monitor) still runs. An instance's agent run doesn't start when the default branch the coordinator started with has invalid committed guardrails at `origin/<default branch>`, or has none there although the coordinator started with them; when origin has none yet (a first hour), the guardrails the coordinator started with stand in.
- A guarded agent run doesn't start when one of its own checkouts (its worktree, or the main checkout) has more than 100 files its secret or hidden patterns list, or when it would be denied more than 2000 paths in all; another worktree past 100 is denied whole instead.
- A guarded run outside an instance doesn't start when its repository's main checkout can't be found: a git directory made apart from its checkout (`git init --separate-git-dir`) records nothing that leads back. An instance's runs always have it, from the instance's repository path.

### Guardrail changes: what each one does

- The `secret_paths` a run is denied are the union of its own checkout's, the main checkout's and the default branch's committed guardrails (at the branch the coordinator started with, never one a config names), each worked out with its own exceptions only, so emptying them in a worktree or adding an exception there drops nothing the others deny. A task's hidden paths take no exception from any config.
- A task's hidden paths and the project's `secret_paths` are denied by the OS sandbox (`sandbox.filesystem.denyRead`) and by `Read(...)` deny rules in every guarded agent run's settings, not only by the guard hook (#890). They are resolved under the run's checkout, the main checkout (the instance's repository path, or the one git records for a submodule) and each linked worktree that exists when the run starts, and `~/` under the run's home. A worktree made while the run goes on is covered too, through a glob over each place worktrees are made (the project's `worktree.root`, the engine's own, and each existing worktree's parent), except for a pattern an exception overlaps. The guard hook matches these paths only inside the run's own checkout. A glob an exception overlaps (`!./.env.example`) is passed as what it matches when the run starts, so the exception stays readable. With the sandbox off, the Read rules still apply.
- A run whose task hides paths (an experiment's) is also denied the repository's git directory and stores (the whole common git directory, every store in the alternates chain as git itself lists it, the real places of links out of those stores, and a custom `lfs.storage`), so `git show <rev>:<hidden path>` can't read a hidden file that was deleted from the worktree.
