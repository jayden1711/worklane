### Guardrail changes: what each one does

- **A pinned required check counts only from a run that started on the judged branch (#943).** A `pull_request` run reads its workflow from the PR's merge ref but posts its checks on the head. So a PR whose head is a commit already on main, and whose base is another branch with its own `ci.yml`, could post green runs of a pinned name on that commit. A workflow-pinned check, and a check pinned to the GitHub Actions App, now counts only from a `push`, `workflow_dispatch` or `schedule` run on that branch, or, on a PR's head, from that PR's own `pull_request` run into it (see R1176c/d below). That holds for PR readiness, the main watch, the updater and `check-pin-block`'s proposals. Such a run that isn't a pass still blocks, as any run from another source does. A fork's PR lists no pull request on its runs, so they never decide a pinned check.
- **The main watch judges a merged PR's pinned checks by what readiness recorded while it was open (#943, R1176a).** GitHub lists the pull request on a workflow run only while it is open, so after a merge a genuine run from a PR into the default branch and a decoy from a closed PR into another base look the same. Readiness now records how it judged each required check on a PR's head (`checks.judged`), and the main watch uses that record for a merged PR's pinned check that reads as missing. A run or status of the name that isn't a pass at merge time, from any source, still fails or waits it first. A PR the harness never judged has no record, and its pinned checks stay missing (unaccounted, fail closed).
- **Stricter run sources for pinned checks (#943, R1176c/d).** For PR readiness, a `pull_request` run counts only when it started on the PR's own head ref, every pull request GitHub lists on it is based on the default branch with the run's commit as its head, and no pull request from that ref or holding that commit, open or closed, is based anywhere else. If those pull requests can't be read, readiness waits; if the backlog can't list them, the check stays missing. A main commit (the main watch's own reads, fix-forward, batches, the updater, `check-pin-block`) counts only `push`, `workflow_dispatch` and `schedule` runs on it, never a `pull_request` run. The main watch uses a readiness record only when it carries the pin the check was judged under and that pin is the one judging now, and only when some run or status of the name exists at merge time; a record alone never accounts a merge.
