### Guardrail changes: what each one does

- **A pinned required check counts only from a run that started on the judged branch (#943).** A `pull_request` run reads its workflow from the PR's merge ref but posts its checks on the head. So a PR whose head is a commit already on main, and whose base is another branch with its own `ci.yml`, could post green runs of a pinned name on that commit. A workflow-pinned check, and a check pinned to the GitHub Actions App, now counts only from a `push`, `workflow_dispatch` or `schedule` run on that branch, or, on a PR's head, from that PR's own `pull_request` run into it (see R1176c/d below). That holds for PR readiness, the main watch, the updater and `check-pin-block`'s proposals. Such a run that isn't a pass still blocks, as any run from another source does. A run whose commit came from a fork (GitHub's `head_repository`) never decides a pinned check (R1176f).
- **The main watch judges a merged PR's pinned checks by what readiness recorded while it was open (#943, R1176a).** GitHub lists the pull request on a workflow run only while it is open, so after a merge a genuine run from a PR into the default branch and a decoy from a closed PR into another base look the same. Readiness now records how it judged each required check on a PR's head (`checks.judged`), and the main watch uses that record for a merged PR's pinned check that reads as missing. A run or status of the name that isn't a pass at merge time, from any source, still fails or waits it first. A PR the harness never judged has no record, and its pinned checks stay missing (unaccounted, fail closed).
- **Stricter run sources for pinned checks (#943, R1176c/d, R1176e/f).** Every judgement of checks now says whether it judges a main commit or a PR's head; one that doesn't is refused, by the compiler and at run time. For a PR's head (readiness, the docs-only fast path's ruleset hold, the batch's merge check, and people's PRs joining a batch), a `pull_request` run counts only when all of these hold:
  - It started on the PR's own head ref, from a commit in this repo (`head_repository`).
  - Every pull request GitHub lists on it is in this repo, based on the default branch, with the run's commit as its head.
  - No pull request from that ref (open or closed), or open and holding that commit, is based anywhere else. (GitHub's `commits/{sha}/pulls` lists only open and merged pull requests.)
  - None of those pull requests ever had its base changed (a `base_ref_changed` in its issue events or timeline). GitHub lists a PR on a run with its current base, so a run made before a base change would otherwise count.

  If those pull requests or their history can't be read, readiness waits; if the backlog can't list them, the check stays missing. A known availability limit (fail closed): a head ref that ever had a pull request into another base, or whose pull request was re-pointed (a stacked PR retargeted at the default branch), never gets a pinned pass; push a new branch for it. A main commit (the main watch's own reads, fix-forward, batches, the updater, `check-pin-block`) counts only `push`, `workflow_dispatch` and `schedule` runs on it, never a `pull_request` run. The main watch uses a readiness record only when it carries the pin the check was judged under and that pin is the one judging now, and only when some run or status of the name exists at merge time; a record alone never accounts a merge.
