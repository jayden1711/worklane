### Upgrading (from v0.5.2)

- **The pre-commit secret scan now scans the index the commit records (#983).** The hook `install --git-hooks` (and an instance's `checkout.sh`) writes runs the engine's own guard entry (`hook-main.js pre-commit`) instead of `gitleaks git --pre-commit --staged`. It reads each changed file of the index git is committing as stored, the way the agents' commit scan does, so a diff driver or textconv in the checkout's config no longer changes what it finds. A commit of named paths is scanned in the index git builds for it. A pre-commit hook it replaced (kept as `pre-commit.before-<cli>`) now runs before the scan, not after, so what that hook stages is scanned too; when it fails, the commit fails. A missing engine or gitleaks, a scan that can't run, or no checkout found fails the commit. Existing checkouts keep the old hook until you run `install --git-hooks` (or `checkout.sh`) again.

### Guardrail changes: what each one does

- **The tool guard refuses more of the ways an agent's line can skip the pre-commit hook, the commit scan's second layer (#983).** In an agent run:
  - `git commit -n` and `--no-verify` in any spelling: bundled short flags such as `-an`, prefixes git accepts for `--no-verify`, or with a `--verify` before it.
  - A commit git would make without the engine's hook. Where the checkout's hooks dir holds the engine's hook, the guard asks git which pre-commit hook file it runs (`git rev-parse --git-path`, which follows `core.hooksPath` through all the config git reads, includes too). A commit is refused when that file isn't the engine's hook or the hook isn't executable.
  - Command strings: the shell matcher now reads the `-c` script of a shell that a known runner (`setsid`, `flock`, `runuser`, …) or `find -exec` runs, and a runner's own command string (`flock F -c '…'`, `runuser -c '…'`). Every rule judges what it reads there like the rest of the line, so a hook-skipping push in such a string is refused too. Any other word that reads as a command line holding a git commit is refused as unread, whatever program gets it (`watch '…'`, `su -c '…'`, `git rebase -x '…'`). Commit and PR messages are exempt.
  - `chmod` is now a write to the files it names, so `chmod -x` on a hook is refused like `rm`.

  Already refused before this change, and pinned by `test/adversarial/commit-scan-index.test.ts`: `core.hooksPath` or an include set by `-c`, `--config-env`, `git config` or `GIT_CONFIG_*`; writes to a git hooks dir or git config file. Ordinary work newly refused in an agent run (measured): a line whose arguments include a command-line-shaped string with a git commit, even as data (`sed -i 's/git commit -n/…/' f`, `printf 'git commit -n'`); a commit in any runner's command string (`setsid bash -c 'git commit -m x'`, as `bash -c` already was). Inferred, not measured: `chmod` on any other path the guard protects from writes. This list is not a proof that nothing else changed.

  Known ways the hook can still be skipped: a commit that a script file, Makefile, package script or interpreter (`python3 -c`, `node -e`) runs, which no command-line guard can see; a hook-skipping push in the string of a program the guard doesn't know as a runner (`watch '…'`); a push behind a shell reserved word (#1125); a `chmod` or config change landing after the guard has decided (a background job); a checkout whose hooks dir has no engine hook (the check above passes there). A working-tree `.gitleaks.toml` still sets the rules both scan layers use (#1128).
