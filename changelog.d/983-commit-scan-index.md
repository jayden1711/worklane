### Upgrading (from v0.5.2)

- **The pre-commit secret scan now scans the index the commit records (#983).** The hook `install --git-hooks` (and an instance's `checkout.sh`) writes runs the engine's own guard entry (`hook-main.js pre-commit`) instead of `gitleaks git --pre-commit --staged`. It reads each changed file of the index git is committing as stored, the way the agents' commit scan does, so a diff driver or textconv in the checkout's config no longer changes what it finds. A commit of named paths is scanned in the index git builds for it. A pre-commit hook it replaced (kept as `pre-commit.before-<cli>`) now runs before the scan, not after, so what that hook stages is scanned too; when it fails, the commit fails. A missing engine or gitleaks, a scan that can't run, or no checkout found fails the commit. Its rules are the project's `.gitleaks.toml` as committed on origin's default branch, else the scanner's built-in rules (#1128), for people's commits too: a working-tree or staged `.gitleaks.toml`, yours included, no longer changes what the hook finds until it is merged. Existing checkouts keep the old hook until you run `install --git-hooks` (or `checkout.sh`) again.
- **An instance's checkout names its own hooks dir in its git config (#983).** `install --git-hooks-only`, which `checkout.sh` runs, now sets `core.hooksPath` in the checkout's own config to that checkout's hooks dir, by absolute path. That file is the coordinator's alone, and git ranks a repository's config above any global config, so no global config an agent's git is pointed at can move the engine's pre-commit and pre-push hooks. The engine's git config check (`git-config-check`, and every guarded git) lets exactly that value through; any other `core.hooksPath` in a repository's config is still refused. Existing checkouts get it when `checkout.sh` runs again. A person's own repo (`install --git-hooks`) is not changed.
- **Agent runs' global git config is a file of the harness's own, with the standard LFS filter (#983).** Every agent run's `GIT_CONFIG_GLOBAL` names a read-only file the runner writes (in a read-only directory of its own under the temp dir), not your `~/.gitconfig`. When `git-lfs` is on the PATH, it holds the large-file filter exactly as `git lfs install` writes it, so an agent's commit stores an LFS-tracked file as a pointer, as yours does. No other setting of yours applies to an agent's git: `core.excludesFile`, `url.*.insteadOf`, commit signing and the rest of `~/.gitconfig` are not read in an agent run.

### Guardrail changes: what each one does

- **The tool guard refuses more of the ways an agent's line can skip the pre-commit hook, the commit scan's second layer (#983).** In an agent run:
  - `git commit -n` and `--no-verify` in any spelling: bundled short flags such as `-an`, prefixes git accepts for `--no-verify`, or with a `--verify` before it.
  - A commit git would make without the engine's hook. Where the checkout's hooks dir holds the engine's hook, the guard asks git which pre-commit hook file it runs (`git rev-parse --git-path`, which follows `core.hooksPath` through the repository, worktree, system and global config, includes too). A commit is refused when that file isn't the engine's hook or the hook isn't executable, and in a process marked as an instance's, whose git reads no global config, it is refused because the guard can't say which hook would run. A commit is also refused when its worktree's repository isn't the one the worktree's admin dir sits in (a rewritten `commondir`), or when that repository's `objects`, `refs`, `refs/heads` or `logs` is a link (R1124s F1).
  - Command strings: the shell matcher now reads the `-c` script of a shell that a known runner (`setsid`, `flock`, `runuser`, …) or `find -exec` runs, and a runner's own command string (`flock F -c '…'`, `runuser -c '…'`). Every rule judges what it reads there like the rest of the line, so a hook-skipping push in such a string is refused too. Any other word that reads as a command line holding a git commit is refused as unread, whatever program gets it (`watch '…'`, `su -c '…'`, `git rebase -x '…'`). Commit and PR messages are exempt.
  - `chmod` is now a write to the files it names, so `chmod -x` on a hook is refused like `rm`.
  - An alias for `commit` is read as git reads it: quotes and backslashes (`"commit"`, `'commit'`, `com"mit"`), and git's global options before the command (`-p commit`, `-c k=v commit`). An option the guard can't step over, or an unbalanced quote, is refused.
  - With `help.autocorrect` on (in config, or given with `-c`), a name that is neither a git command nor an alias is refused, since git may run the commit it corrects it to (`git comit -n`). The push rule already read it this way.
  - Every staged file is scanned, even when two entries land on one file once written out: names that aren't UTF-8, and any pair the file system folds together (case, NFC/NFD, and on APFS `ß`/`ss`, `ſ`/`s`, `µ`/`μ`, `ς`/`σ` and more). Each entry is created exclusively, and one whose name is taken goes in another scan root. A case variant of the scanner's own file names (`.GITLEAKSIGNORE`) goes a folder lower, as the exact names do, so it can't set the scan's rules or ignores.
  - A git name with a dot, which git may run as an alias in a subsection (`[alias "Ci"] x = commit` runs as `git ci.x`), is refused, for commits and pushes. So is any name that isn't git's own in a process marked as an instance's, whose git reads no global config.
  - A folder moved, copied or linked into a place git reads config or hooks from (a git dir, the user's config folder or its `git/`), and a file moved into one (`mv /tmp/.gitconfig ~`), count as writes to git config. This holds for the folder's own name, spelt as the guard spells paths. It does not hold for another name for the same folder (R1124l D1): see the limits below.
  - A write to the user's or a repository's git config or hooks is caught in the spellings the guard models (R1124i, R1124j, R1124k). Those spellings are: braces; `~`, `$HOME`, `$XDG_CONFIG_HOME` and the line's own variables; any other plain variable tried as each config folder; `./` and `..`; the line's `cd`s; and case and Unicode folding as APFS reads names (`~/.GITCONFIG`, `~/.config/Git`, `.GIT/config`). A glob counts when it could match a config file or folder; as in bash, `*`, `?` and `[…]` never match a name's leading dot. A write destination is any of: a redirect; every operand of `mv`, `cp`, `ln`, `install` or `rsync`; `tee`'s files; `curl -o` and `wget -O`; `dd of=`; an in-place `sed` or `perl`'s files. A destination the guard can't spell out is refused rather than guessed at (R1124k): a command substitution, a parameter operator (`${F%x}`, `${F/x/}`, `${X:-y}`), a line variable holding one, too many variables, or an unreadable glob. Write it with a literal path. A line that runs `eval` is refused. Other path-like words of a command that doesn't only read, where they can be spelt out, are judged only by their shape (a git config file, or a hooks dir or config inside a git dir; a bare git dir is not a shape, R1124n E1), in the directories the line's `cd`s are followed to. Only a write destination is also judged as a folder put in place (R1124l D2). A line that writes to paths it reads at run time (`xargs`, `parallel`, `read`, `find -exec`) is refused when any of its words reaches HOME or a folder above it.
  - **No agent run's git reads the user's git config (the owner's decision 6c).** The runner sets `GIT_CONFIG_GLOBAL` for every agent run, after anything passed in, to the harness's own read-only file (above), so git reads neither `~/.gitconfig` nor `~/.config/git/config`, and `git config --global` can't write one. (The coordinator's own git already read none, #926.)
  - **The guarantee (the owner's decision): pushes to origin's default branch land only through `checkedPush` (authority), whatever the agent's shell does; the hook and the guard are hints.** This holds for an instance whose agents run as their own OS user (`run_as`). Such an agent run holds no credential origin accepts. `checkedPush`, the one credentialed push, refuses the default branch in code, except the direct land of `land_mode: direct`, which is `checkedPush`'s own push by design. The named limits are local mode, an instance with `allow_same_user: true` (agents run as the coordinator, so they can reach its App key and the checkout's config), and remotes an agent can write without a credential (below). The hook is a sturdier hint in an instance's checkout: its hooks dir is named in the checkout's own config, which git ranks above any global config, so what an agent's shell sets `GIT_CONFIG_GLOBAL` to, in any spelling, doesn't move it (measured: R1124p's three pushes, `printf -v`, `read` and `declare +x`, now run the engine's pre-push hook and are refused). The guard's `GIT_CONFIG*` refusals are a hint too: it refuses a line that sets a `GIT_CONFIG*` variable by assignment or `export` (except `GIT_CONFIG_GLOBAL` at the null device), unsets one (`unset`, `export -n`, `env -u NAME`), or empties the environment (`env -i`, `env -`). It does not refuse these, measured by R1124p: `printf -v`, `read`, `mapfile`, `getopts` or `declare -n` into `GIT_CONFIG_GLOBAL`, `declare`/`typeset` with `+x`, an attached `env -uNAME` or `env --unset=NAME` in a line without a push, `exec -c`, `setpriv --reset-env`, and GNU `env --ignore-env`. Each of these only changes which global config git reads.
  - **More writers modelled (R1124o).** `sort -o`/`--output`, `uniq`'s second operand, `tree -o`, and a git command's `--output`/`--output-directory` (`git log`, `show`, `diff`, `format-patch`) are write destinations. A command with an output file is no longer a plain reader. A `git config` write whose key the guard can't spell out (a variable, a substitution, braces or a glob) is refused, since it may be `core.hooksPath`. `git` given as an argument to a program the guard doesn't know as a runner (`arch`, `xcrun`, `script`, …) is refused when a `push`, `config`, `send-pack` or `--no-verify` follows it. `xcrun git push --no-verify` was allowed before this PR too (inferred: main's runner list lacks `xcrun` the same way; not run on main). A line that reads names (`while read -r f`, `mapfile`) has only its commands that may write judged as writing paths read at run time; `echo`, `printf`, `read` and plain readers aren't (R1124o D5). Every word of `sort`, `uniq` and `tree` is a write destination, so an output file in any spelling counts: a cluster (`sort -uo F`), an abbreviation (`--outp=F`, `--out F`), or uniq's output after an option value (`uniq -f 1 IN OUT`) (R1124p F2). So `sort .git/config` is refused too, as a write.

  Already refused before this change, and pinned by `test/adversarial/commit-scan-index.test.ts`: `core.hooksPath` or an include set by `-c`, `--config-env`, `git config` or `GIT_CONFIG_*`; writes to a git hooks dir or git config file. Ordinary work newly refused in an agent run (measured): any `GIT_CONFIG*` assignment other than `GIT_CONFIG_GLOBAL` at the null device, `unset GIT_CONFIG_*`, and `env -i …`/`env - …` (6c); a `git config` write with a non-literal key (`git config "$K" v`); `git` as an argument of an unknown program followed by `push` or `config` (`xcrun git push`); a write destination spelt with a substitution, including `mkdir -p "$(dirname out/x/y)"` and `touch "$(date +%s).log"` (R1124o); a `find` that deletes or runs a command under a path the guard can't spell out (`find "$DIR" -name '*.log' -delete`, R1124l D4); a write destination spelt with a substitution or parameter operator (`> "$(mktemp)"`, `cp a "${OUT%/}"`), and any `eval`; a command that isn't a plain reader and names a git config file or hooks dir as an argument, even to read it (`cp .git/config /tmp/x`; `cat`, `ls`, `git config --get` and the like still may); a line whose arguments include a command-line-shaped string with a git commit, even as data (`sed -i 's/git commit -n/…/' f`, `printf 'git commit -n'`); a commit in any runner's command string (`setsid bash -c 'git commit -m x'`, as `bash -c` already was); `sort`, `uniq` or `tree` naming a git config file or hooks dir in any word, even to read it (`sort .git/config`, R1124p F2). Inferred, not measured: `chmod` on any other path the guard protects from writes. This list is not a proof that nothing else changed.

  What the guarantee covers, and its named limits (measured on a scratch checkout with a local bare remote, R1124p's harness, except where it says inferred):
    - **The guarantee (instances with `run_as`):** a push to origin's default branch lands only through `checkedPush`, whatever the agent's shell does. An agent run as its own OS user has no credential origin accepts. `checkedPush`, the only credentialed push, refuses the default branch in code, except the direct land (`land_mode: direct`), which is its own push. (Inferred from the code: the runner's environment allowlist and credential-helper reset, the agent user's separate home and the App helper reading the key from the coordinator's instance home; not run against GitHub here.)
    - **Hints, not the guarantee:** the engine's pre-commit and pre-push hooks and the guard's refusals. In an instance's checkout, global config can't move the hooks git runs, however the agent's shell points git at it.
    - **Limit: the hooks can still be skipped**, so for a remote an agent can write without a credential (a local path) nothing stops the push; its refs the agent could write directly anyway. For a commit, the land queue's range re-scan still applies (inferred). The ways:
      - command-scope config, which git ranks above the checkout's (`git -c core.hooksPath=…`, `GIT_CONFIG_COUNT`/`KEY`/`VALUE` pairs, `GIT_CONFIG_PARAMETERS`);
      - `git push --no-verify` and `git commit -n`;
      - git plumbing, which runs no hook: `git hash-object -w`, `git commit-tree`, `git update-ref` (each allowed, R1124r: a secret reached a branch this way). `objects/` and `refs/` are agent-writable by design (#926);
      - another repository for the same refs: `GIT_DIR`/`GIT_COMMON_DIR` at a copy, or a rewrite of the worktree's `commondir` or its `.git` file to a common dir of the agent's own whose objects and refs link to the real ones (R1124s F1). A commit there is now refused when the decision is made (the common dir isn't the one the worktree's admin dir sits in, or its objects, refs or logs are links), but a rewrite after the decision, or a commit by plumbing, isn't seen;
      - any of these run by an interpreter or script (`python3 -c "os.system('git push --no-verify …')"`: allowed, and it landed on the local remote).

      The guard refuses the spellings it models.
    - **Limit: an instance with `allow_same_user: true`** (root's `policy.yaml`, off by default). Agents run as the coordinator user. The App key, the checkout's config and the pin are then the agent's too, and project commands run unsandboxed, so an agent can mint a token and push without `checkedPush` (R1124r F1, inferred from the code). Not covered.
    - **Limit: local mode (no agent user).** Agents run as you, can write the repository's config and hooks, and can reach your credentials (your keychain's git helper, your SSH keys) from any program they run. There the hook and the guard are the only layers, as before. A root-owned user git config for agent users on servers is #1240.

  Known ways the hook can still be skipped by a line the guard allows: a commit that a script file, Makefile, package script or interpreter (`python3 -c`, `node -e`) runs, which no command-line guard can see; a hook-skipping push in the string of a program the guard doesn't know as a runner (`watch '…'`); a push behind a shell reserved word (#1125); a `chmod` or config change landing after the guard has decided (a background job); a checkout whose hooks dir has no engine hook (the check above passes there). A write to a git config whose path no word of the line spells: a path an interpreter builds at run time (`node -e`, `python3 -c`, a script), or one `xargs` or `read` takes from a file or a pipe (`xargs cp gc < list`, `echo ~/.gitconfi | sed 's/$/g/' | xargs cp gc`). A git config written as the content of a folder a command fills, where the line names only the folder (R1124l D3, R1124m):
    - an archive extracted into HOME: `tar -xf e.tar -C ~` (with `-s` renaming an entry, into `~/.config` too), `unzip -o e.zip -d ~`, `cd ~ && cpio -idm < a.cpio`, `pax`, `bsdtar`;
    - a recursive copy of a folder's contents into HOME: `cp -a src/. ~`, `cp -R src/ ~` (BSD cp), `rsync -a src/ ~/`, `ditto src ~`;
    - `patch -d ~ -p1 < p.diff`.

  A config folder reached by another name (R1124l D1): a symlink, a firmlink such as `/System/Volumes/Data$HOME` on macOS, `/private$HOME` for a HOME under `/var`, or `/proc/self/root$HOME` on Linux. The guard compares path strings and never resolves links.

  A folder a command creates as a destination the guard doesn't model (R1124l D2, R1124n): `git clone r "$HOME/.config/git"`, `git -C "$HOME/.config" clone r git`, and `git worktree add` into a config folder; and a clone into a git dir (`git clone r sub/.git`), whose tree then is that repository's git dir.

  The commit decision after such a write still refuses a planted `core.hooksPath`, include or commit alias (measured by R1124m), so these leave the same window as a config change landing after the guard has decided (R1124l measured the same for D1-D3 in a separate call: `commitHookSkipped` and the alias reader refused the commit). String matching on the command line can't close these. In an agent run the user git config is out of reach (6c), and in an instance's checkout the repository's config and hooks are the coordinator's (#926), so such a write no longer moves the hooks there; it still changes your own git outside the harness.
